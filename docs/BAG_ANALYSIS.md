# Анализ записанных bag-файлов

Состояние на 2026-10-23. Источник: ваши записи `for_odometry` (`/lowstate`, 13.8 с), `sample_of_walking` (`/lowstate`, 32.7 с,
ходьба), `lidar-imu` (`/livox/lidar`, `/livox/imu`, 48.7 с) и `low_cmd` (`/lowcmd`, не используется: не сенсорика).
Разбирал сам `.db3` без ROS скриптами из [tools/bag_analysis](../tools/bag_analysis); конвертеры пакетов на этих данных
**не запускались** (в моей среде нет ROS), поэтому проверены допущения о данных, а не сами узлы.

Повторить у себя (нужны только Python 3 и numpy):

```bash
python3 src/tools/bag_analysis/analyze_lowstate.py ~/.../for_odometry ~/.../sample_of_walking
python3 src/tools/bag_analysis/analyze_livox.py ~/.../lidar-imu
```

## Что подтвердилось

| Вопрос | Результат |
|---|---|
| Порядок кватерниона Unitree | В обоих bag (22 479 сообщений) кватернион как $(w,x,y,z)$ совпадает с полем `rpy` того же сообщения с точностью $\le 1.5\cdot10^{-7}$ рад. Если читать его как $(x,y,z,w)$, расхождение доходит до $3.14$ рад. Это подтверждает исправление в `imu_converter` и `odom_converter` |
| Норма кватерниона | $1.000000$ во всех сообщениях, нулевых и NaN нет |
| Тип сообщения | `unitree_go/msg/LowState`, как и ожидают конвертеры |
| Частота `/lowstate` | около 500 Гц (шаг поля `tick` — 2 мс) |
| `point_num` лидара | во всех 11 кадрах равен длине массива `points`; ветка `min(point_num, points.size())` на реальных данных не сработала |
| Плотность лидара | 3936–4128 точек за 20 мс, то есть около 200 тыс. точек/с, как у MID360 |

## Что показали данные и чего я не ожидал

1. **Нулевой кватернион в bag не встречается** (0 из 22 479). Защита в `imu_converter` по-прежнему ничем не подтверждена:
   вреда от неё нет, но и пользы мы не видели. Запись шла уже при работающем роботе, момент старта она не покрывает.
2. **Оценка шума IMU** (по самому тихому окну 1 с в каждом bag, это *верхняя* оценка: робот мог балансировать):
   гироскоп $\sigma\approx0.010$ рад/с, смещение около $0.007$ рад/с по осям $y, z$; акселерометр
   $\sigma\approx0.05\ldots0.10$ м/с². Отсюда стартовые значения параметров:
   `angular_velocity_variance` $\approx 10^{-4}$, `linear_acceleration_variance` $\approx 10^{-2}$. Для ориентации
   оценки нет. Гироскоп квантован с шагом около 0.0021 рад/с.
3. **Нулевые точки лидара: 19.2 %** (8445 из 43 968) имеют дальность 0. Все точки с тегами 128 и 192 нулевые, ещё около
   4.6 тыс. с тегом 0. `livox_to_pointcloud2` копирует их как есть, поэтому в облаке есть скопление в начале координат.
   В `pointcloud_to_laserscan` их убирает `range_min: 0.3`, а облако для других потребителей (SLAM, RViz) остаётся с мусором.
4. **Временные штампы лидара опережают время записи на 8–10 с** (IMU лидара: от 8.1 до 9.7 с). Либо часы лидара не
   синхронизированы с компьютером, либо запись шла на другой машине с другим временем. Пока причина неизвестна, но
   пакеты `imu_converter` и `odom_converter` ставят штамп по часам ROS, а драйвер Livox использует время лидара,
   и для динамических TF и SLAM это важно. Проверка на железе — T54.
5. **Запись неполная**, по ней нельзя судить о частотах: IMU лидара 174 Гц вместо около 200, 60 пауз длиннее 15 мс
   (самая длинная 450 мс); лидар: 10 подряд идущих кадров (шаг 20 мс), затем пауза 2.5 с, всего 11 кадров из ожидаемых
   около 2400. Похоже на потери при записи (сеть или DDS), а не обязательно на поведение драйвера: сверьте с T14.
6. **Ускорение IMU Livox в единицах g, не в м/с²** (среднее по модулю 0.985). Топик `/sensors/imu/livox` нарушает
   REP-145, и смешивать его с IMU Unitree (м/с²) в фильтре или SLAM без масштаба $9.81$ нельзя. Ориентация там
   `(0,0,0,1)` с нулевой ковариацией, то есть формально «известна», фактически её нет.
7. **Имена фреймов в bag**: лидар `mid360_link`, IMU лидара `livox_frame`. Текущий launch задаёт `livox_frame` для обоих
   (один параметр `frame_id`), запись сделана на старой конфигурации.

## Чего bag не даёт

Положение и наклон лидара (облако уже с применённым `extrinsic_parameter`), систему координат скорости
(`SportModeState` в bag нет), сетевые частоты драйвера, поведение при старте робота.

## Симуляция

В списке топиков симуляции есть `/sportmodestate`, а у `odom_converter` по умолчанию `odommodestate`, поэтому
нужно `-p sport_topic:=sportmodestate`. Кроме того, при старте узел вызывает `OdomClient.EnableOdom()`, которому нужен
сервис реального робота; в симуляции он, скорее всего, не ответит. Для проверки на симуляции понадобится параметр,
который пропускает этот шаг.
